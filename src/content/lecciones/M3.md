## Qué es SDD

**Spec-Driven Development**: escribir una especificación de comportamiento *antes* del código, y usarla como la fuente de verdad que dirige al agente. La idea base es "documentation first" llevada en serio: en vez de que el código sea lo único real y los docs un reflejo aproximado, la spec es el artefacto primario y el código una consecuencia.

Con agentes, esto deja de ser un lujo de metodología y pasa a ser una necesidad técnica: el agente no tiene tu contexto mental. La spec es la forma de transferir intención.

## La inversión de poder

El manifiesto de GitHub Spec Kit lo enuncia como inversión: **el código sirve a la spec, no la spec al código**. Durante décadas la documentación perseguía al código (siempre desactualizada, siempre opcional). En SDD la relación se da vuelta: si hay conflicto entre spec y código, el que está mal es el código.

"El código es la última milla" — la frase del manifiesto resume la tesis: lo difícil del software (entender el problema, decidir el comportamiento) pasa a vivir en la spec; la generación de código es la parte más mecánica.

## ¿Qué es exactamente una spec?

Siguiendo a Böckeler (martinfowler.com), una spec es un artefacto:

- **Estructurado**: formato conocido, secciones previsibles (user stories, criterios de aceptación, requisitos no funcionales).
- **Orientado a comportamiento**: qué hace el sistema, no qué clases contiene.
- **En lenguaje natural**: legible por humanos y ejecutable por agentes.
- **Que expresa funcionalidad y guía**: no es documentación decorativa; es el input que dirige la implementación.

## Spec vs. memory bank / reglas

Confusión frecuente que conviene resolver temprano:

| Artefacto | Alcance | Vida |
|---|---|---|
| **Spec** | Una feature/tarea | Nace con la feature, se archiva o evoluciona con ella |
| **Memory bank** (AGENTS.md, constitution, steering) | Todas las sesiones del repo | Permanente, cambia lento |

AGENTS.md no es "la spec del repo": es el mapa de navegación y las convenciones. La spec es por tarea. Mezclarlos produce AGENTS.md gigantes que nadie lee y specs llenas de reglas globales repetidas.

## Los tres niveles de SDD

Böckeler distingue tres grados crecientes de compromiso:

1. **Spec-first**: la spec se escribe antes de implementar y dirige *esa* tarea. Después puede quedar desactualizada sin drama — la mayoría de los flujos actuales (Spec Kit, Kiro) viven acá.
2. **Spec-anchored**: la spec se mantiene como artefacto vivo a lo largo de la vida de la feature; los cambios pasan por la spec. OpenSpec empuja hacia acá (specs en `openspec/specs/` + cambios como deltas).
3. **Spec-as-source**: el humano solo edita la spec; el código se regenera (`// GENERATED FROM SPEC — DO NOT EDIT`). Tessl lo explora. Es el nivel más radical: convierte la spec en el "lenguaje de programación" y al agente en el compilador.

## Principios del enfoque (spec-kit)

- **Specs como lingua franca**: el mismo artefacto sirve para humano y agente.
- **Specs ejecutables**: lo suficientemente precisas para que un agente las transforme en código.
- **Refinamiento continuo**: clarify → plan → checklist; la spec se pule por fases.
- **Contexto guiado por investigación**: research.md existe para que el plan no sea adivinanza.
- **Feedback bidireccional**: lo que aprende la implementación vuelve a la spec.
- **Branching**: generar implementaciones alternativas de la misma spec para comparar.

## Relación con prácticas clásicas

SDD tiene parientes claros y conviene no fingir que inventó todo:

- **PRD**: la spec funcional hereda su rol.
- **BDD/Gherkin**: Given/When/Then ya era "specs ejecutables"; SDD lo recupera para dirigir agentes.
- **TDD**: los criterios de aceptación juegan el rol de los tests escritos primero.
- **ADRs / Design Docs**: capturan decisiones; en SDD quedan como decisiones de la spec o del plan.
- **Model-Driven Development**: el paralelo más incómodo — MDD también prometía "el modelo es la fuente". La diferencia: hoy el "compilador" (el LLM) es de propósito general y la spec es prosa estructurada, no UML.

## Para llevar

- SDD = spec primero, código después; el código sirve a la spec.
- Elegí conscientemente el nivel: first (liviano), anchored (mantenida), as-source (regenerado).
- Spec ≠ memory bank: una es por tarea, la otra es permanente.
