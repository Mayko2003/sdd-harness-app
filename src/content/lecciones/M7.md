## El modelo mental

El marco de Böckeler (*Harness engineering for coding agent users*) divide todo el harness en dos familias, tomadas de la teoría de control:

- **Guías (feedforward)**: actúan *antes* de que el agente trabaje. Anticipan y orientan.
- **Sensores (feedback)**: actúan *después*. Observan lo que salió y permiten la autocorrección.

Un agente con solo guías se equivoca elegante; uno con solo sensores detecta errores que podría haber evitado. El harness maduro diseña ambos.

## Guías (feedforward)

Todo lo que pone al agente en el camino correcto antes de empezar:

- **AGENTS.md / CLAUDE.md**: el mapa del repo y las convenciones.
- **Skills**: procedimientos empaquetados para tareas recurrentes.
- **Scripts de bootstrap**: `init.sh`, seeds, setup de entorno reproducible.
- **Codemods y scaffolding**: patrones que el agente imita en vez de inventar.
- **La spec** (acá SDD y harness se tocan): la spec es la guía feedforward por excelencia — dice qué construir antes de construir.

## Sensores (feedback)

Todo lo que observa el resultado y produce señal de corrección:

- **Tests** (unitarios, integración, E2E, aceptación).
- **Linters y type checkers**.
- **Revisión por IA** (otro modelo juzga el diff).
- **Checks de CI** que el agente puede consultar.

Tip de Böckeler: escribir los mensajes de linter **para el LLM** — no "error TS2304" sino el error + la instrucción de corrección en prosa. El sensor no solo detecta; enseña cómo corregir.

## Computacional vs. inferencial

Segunda división, esta por naturaleza del mecanismo:

| | Computacional | Inferencial |
|---|---|---|
| Qué es | Determinista, rápido, barato | Semántico, lento, caro, no determinista |
| Ejemplos | Lint, types, tests, hooks | LLM-as-judge, review por agente |
| Regla | Preferir siempre que alcance | Reservar para lo que lo determinista no captura |

Si un linter puede detectar el problema, no necesitás un modelo que lo detecte. Los sensores computacionales son el primer piso; lo inferencial va encima.

## El steering loop

El trabajo del humano cambia de forma: ya no escribe código — **itera sobre el harness**. El loop es:

```
agente falla → diagnóstico → ¿falta guía o falta sensor? → mejorar harness → repetir
```

Si el mismo problema aparece dos veces, es un bug del harness, no del agente (regla de Hashimoto aplicada al modelo mental).

## Timing: keep quality left

Dónde corre cada check importa tanto como qué checkea:

- **Antes del commit**: lint, types, tests rápidos — baratos, inmediatos.
- **En CI**: la suite completa, E2E, checks de integración.
- **Continuo**: drift del codebase, dead code, dependencias vulnerables.
- **Runtime**: SLOs, logs, métricas — el comportamiento real en producción.

Mover calidad "a la izquierda" (antes en el pipeline) abarata cada corrección: un error detectado por el type checker cuesta tokens de una tool call; detectado en producción cuesta un incidente.

## Categorías de regulación

Böckeler agrupa los harnesses por *qué regulan*:

1. **Maintainability harness**: calidad interna — lint, tests, tipos, deuda. El más maduro hoy; es lo que ya hacemos bien.
2. **Architecture fitness harness**: fitness functions — límites de módulos, performance, observabilidad, acoplamiento. Semi-maduro.
3. **Behaviour harness**: *¿el sistema hace lo que tiene que hacer?* El problema abierto del campo — y exactamente donde entra SDD: la spec define el comportamiento, los escenarios de aceptación se convierten en sensores.

## Harnessability

No todos los codebases son igual de "harnesseables": tipado fuerte, tests rápidos, límites de módulos claros y APIs previsibles hacen que los sensores sean más informativos y las guías más aplicables. La ley de Ashby (variedad requisita) da la intuición teórica: el sistema de control necesita tanta variedad como el sistema que controla — un harness simple no puede regular un codebase caótico.

## Para llevar

- Guías antes (feedforward), sensores después (feedback). Diseñá ambos.
- Computacional primero, inferencial donde el determinismo no alcanza.
- El steering loop es tu nuevo trabajo: error → guía o sensor que faltaba → harness mejor.
- Behaviour harness = el problema abierto; SDD es su respuesta natural.
