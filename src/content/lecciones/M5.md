## Panorama

| Herramienta | Nivel SDD | Artefactos / workflow | Idea distintiva |
|---|---|---|---|
| **GitHub Spec Kit** | spec-first → anchored | `constitution → specify → clarify → plan → checklist → tasks → analyze → implement`; `spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/`, `tasks.md` | **Constitution** (principios inmutables), checklists como definition-of-done por fase, agnóstico de agente |
| **Kiro** (AWS) | spec-first | `requirements.md` (EARS) → `design.md` → `tasks.md` en `.kiro/specs/` | IDE propio, **steering** (product/structure/tech), gates de aprobación por fase, modo Quick Spec vs. Vibe |
| **OpenSpec** (Fission AI) | spec-anchored | `openspec/specs/` (verdad) + `openspec/changes/<cambio>/` (proposal + delta specs + design + tasks) → **archive** fusiona | Liviano, pensado para brownfield, ciclo propose → apply → archive |
| **Tessl** | anchored → spec-as-source | Specs por archivo con `@generate`/`@test`; Spec Registry | Explora spec-as-source; specs como dependencias instalables (usage specs de librerías) |
| **BMAD Method** | spec-first multi-agente | Brainstorm → PRD → Arquitectura/ADR → Epics → Stories → Readiness → Implementación → Code review | Agentes por rol: analyst, PM, architect, dev, QA, UX |

## Spec Kit

El de GitHub es el más "proceso completo": cada fase produce un artefacto revisable y hay checklists que actúan como puertas de calidad. La **constitution** es su contribución conceptual más importante: un archivo de principios inmutables del proyecto (ej. "toda feature tiene tests", "APIs versionadas") que condiciona todas las fases. Es el memory bank aplicado al proceso.

Sirve bien cuando: features medianas/grandes, equipos que quieren gates explícitos, querés que el agente justifique su plan antes de tocar código.

## Kiro

El IDE de AWS integra el flujo en la UI: escribís specs que producen `requirements.md` en EARS, `design.md` y `tasks.md`, con aprobación humana entre fases. El **steering** son archivos de contexto permanente (qué es el producto, cómo está estructurado el repo, qué stack) — su versión del memory bank. Los modos "Quick Spec" y "Vibe" reconocen que no toda tarea merece el pipeline completo.

## OpenSpec

La opción liviana para codebases que ya existen. Dos directorios: `specs/` con la verdad actual y `changes/` con propuestas pendientes. Cada propuesta lleva *por qué*, *delta specs* (ADDED/MODIFIED/REMOVED), diseño y tasks. Al archivar, los deltas se fusionan en la spec canónica. Menos ceremonia que Spec Kit, mejor mantenimiento continuo — spec-anchored de verdad.

## Tessl

La apuesta más radical: el archivo de spec lleva anotaciones (`@generate`, `@test`) y el código se regenera desde la spec — spec-as-source real. Su **Spec Registry** propone algo interesante: specs de uso de librerías como dependencias instalables, para que el agente sepa usar una librería sin rebuscar documentación cada vez.

## BMAD

Workflow de roles: un "analista" hace brainstorm, un "PM" escribe el PRD, un "arquitecto" los ADRs, un "dev" implementa stories con criterios de aceptación. Es Spec Kit con drama multi-personaje — el valor real es la **separación de contextos por fase** (cada rol arranca fresco con el artefacto anterior), más que los nombres de personajes.

## Cómo elegir

- **Bug chico / fix**: ninguna herramienta completa; spec de 5 líneas o directamente un issue claro.
- **Feature mediana**: OpenSpec o flujo liviano tipo Pocock (módulo siguiente).
- **Feature grande / greenfield**: Spec Kit o BMAD si querés el proceso completo con gates.
- **Equipo que adopta la práctica**: empezar por Spec Kit (estructura clara) y podar lo que sobre.
- **Spec-as-source**: Tessl si querés la frontera — pero aceptá que es exploratorio.

## Cuándo NO usar SDD

- Prototipos descartables: la spec cuesta más que el experimento.
- Cambios triviales cuya descripción es la spec.
- Cuando la spec quedará sin mantenimiento: una spec muerta es peor que ninguna (enseña información falsa).

## Laboratorio

Implementar la misma feature con Spec Kit, Kiro y OpenSpec y comparar: cantidad de artefactos, cuánto se revisó a mano, cuánto se desvió el código de la spec, cuánto quedó mantenible el doc después.
