## La síntesis

Los dos campos resultan ser el mismo sistema visto desde dos ángulos:

- **SDD** responde "¿qué tiene que construir el agente?" — la spec es la intención formalizada.
- **Harness** responde "¿cómo trabaja el agente y cómo se corrige?" — el entorno de guías y sensores.

En el vocabulario del módulo 7, la conexión es directa:

> **La spec es la guía feedforward del behaviour harness. Los escenarios de aceptación son sus sensores.**

## La spec como guía

Una spec bien escrita hace el trabajo de una guía: pone al agente en el camino correcto *antes* de que escriba una línea. Es feedforward puro — anticipa el comportamiento deseado y lo fija en un artefacto revisable.

## Los escenarios como sensores

Los escenarios Given/When/Then y los criterios de aceptación se traducen a tests. Esos tests son los sensores del *behaviour harness*: observan lo que salió y permiten la autocorrección. Ahí se cierra el problema abierto de Böckeler (el behaviour harness como la categoría menos madura): SDD aporta exactamente lo que faltaba — una forma de especificar comportamiento verificable.

```
spec (guía) → implementación → tests de aceptación (sensores) → corrección
```

## Constitution y steering como memoria del harness

La constitution de Spec Kit, el steering de Kiro, AGENTS.md: son el memory bank — reglas que aplican a *todas* las tareas, no a una. En términos de harness son una guía permanente; en términos de SDD son los principios que toda spec hereda. Mismo artefacto, dos lecturas.

## El pipeline integrado

La arquitectura completa, de punta a punta:

```
spec → plan → tasks → implementación en loop agéntico
     → sensores (tests, lint, revisión IA) → PR → archivar spec
```

- **spec**: intención + criterios de aceptación (guía).
- **plan**: decisiones de cómo (research.md, data-model.md).
- **tasks**: unidades de una ventana de contexto (DAG).
- **loop**: el agente ejecuta con el harness a su alrededor.
- **sensores**: tests (aceptación), lint/types (maintainability), review por IA.
- **PR → archive**: la spec se fusiona como verdad actualizada (OpenSpec) o se archiva.

## Trazabilidad spec ↔ código ↔ tests

La cadena requisito → tarea → test → código permite dos operaciones valiosas:

- **Verificación de cobertura**: todo requisito tiene test; todo test mapea a un requisito.
- **Detección de drift**: cuando el código diverge de la spec, la pregunta "¿qué es verdad?" tiene respuesta — y herramientas que la chequean (analyze de Spec Kit, linters de specs, agentes de doc-gardening).

El drift spec↔código es el nuevo "comentario desactualizado": una spec anchored que nadie verifica se convierte en ficción.

## Exec plans: planes como artefactos versionados

Los `docs/exec-plans/` de OpenAI y los `tasks.md` de Spec Kit son lo mismo visto desde abajo: **el plan es un artefacto versionado que sobrevive al contexto que lo creó**. El plan deja de ser algo que el agente "piensa" y pasa a ser algo que *existe* — revisable por humanos, retomable por otros agentes, auditable después.

## Para llevar

- Spec = guía feedforward; escenarios de aceptación = sensores. SDD es la respuesta al behaviour harness.
- Memory bank (constitution/steering) es la parte permanente del harness; la spec es la parte por-tarea.
- El pipeline completo conecta spec → plan → tasks → loop → sensores → PR → archivo.
- Trazabilidad y detección de drift son lo que separa "spec anchored" de "spec decorativa".
