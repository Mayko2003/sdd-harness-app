## El problema de las horas

Un agente que trabaja 5 minutos no necesita estructura de memoria: la ventana alcanza. Uno que trabaja 6+ horas necesita mecanismos explícitos para no perder el hilo, no repetir trabajo y no degradarse con el context rot. Los patrones que siguen son los que emergieron para eso.

## Initializer agent + coding agent (Anthropic)

El patrón de *Effective harnesses for long-running agents*:

- Un **initializer** corre una vez: levanta el entorno, crea `init.sh`, genera un archivo de progreso y la lista de features pendientes.
- El **coding agent** trabaja por sesiones: lee el progreso, toma *una* feature, la implementa, la commitea, actualiza el archivo y deja el entorno **limpio** — como si el próximo agente fuera a arrancar en frío.

La disciplina es la clave: cada sesión confía en los artefactos (init.sh, progress file, git log), no en la memoria de la sesión anterior. Git como log recuperable.

## Planner / Generator / Evaluator

Separar los tres roles en contextos distintos (Anthropic, mar 2026):

- **Planner**: produce el plan — contexto de exploración, decisiones.
- **Generator**: implementa — sufre la presión de contexto del código.
- **Evaluator**: juzga — recibe el diff limpio, evalúa contra spec/estándares.

La separación combate la **"context anxiety"**: el fenómeno por el que el agente que implementó defiende su propio trabajo, o repite errores porque su contexto está contaminado con los intentos fallidos. El evaluador sin historia ve el trabajo fresco.

Elegir **reset vs. compaction** por fase: compaction conserva el hilo narrativo; reset da contexto limpio con un artefacto de handoff. Los cambios de fase (plan→implementación, implementación→review) son puntos naturales de reset.

## Ralph Wiggum loop (Geoffrey Huntley)

El experimento artesanal que se volvió patrón de culto:

```bash
while :; do cat PROMPT.md | claude ; done
```

Un loop infinito donde cada iteración es una ventana fresca con el mismo prompt. Para que funcione:

- **Una tarea por iteración** — la unidad entra en un contexto nuevo.
- **Specs en carpeta** — el estado vive en archivos, no en la conversación.
- El contexto principal actúa como **scheduler de subagentes**: delega, no ejecuta.

Es la forma extrema del principio "un ticket = una ventana": la continuidad se garantiza por los artefactos en disco, no por la memoria del loop.

## Revisión agente-a-agente

OpenAI describe el patrón de revisión iterativa: agentes revisores distintos del implementador, iterando hasta que todos aprueban. El punto práctico: el revisor ve el diff con contexto limpio (sin la historia de por qué se hizo así) — detecta lo que el implementador, con su contexto contaminado de intentos previos, ya no puede ver.

## Operación continua

La regla operativa de Hashimoto: *"always have an agent running"*. Los agentes en background (colas de tareas, worktrees paralelos, sesiones nocturnas) convierten la ingeniería asistida en un sistema de producción: el cuello de botella deja de ser el tiempo del agente y pasa a ser la **revisión humana y la calidad de las specs**.

## Cuándo NO multi-agente

Multi-agente no es gratis. Es la analogía con microservicios: subagentes no deterministas coordinándose = sistemas distribuidos con nondeterminismo. Los costos reales:

- Overhead de coordinación (handoffs, merges de worktrees).
- Debugging multiplicado: ¿falló el agente o la orquestación?
- Complejidad que solo se paga si la tarea es realmente paralela o realmente larga.

Si la tarea cabe en una ventana y no se paraleliza, un solo agente con buen harness gana.

## Para llevar

- Trabajo largo = estado en artefactos (init.sh, progress file, git), sesiones que arrancan limpias.
- Separar planner/generator/evaluator = contextos especializados que combaten context anxiety.
- Ralph: una tarea por loop, el disco como memoria.
- Multi-agente para trabajo realmente paralelo o largo; el resto es overhead.
