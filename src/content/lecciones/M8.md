## Archivos de instrucciones: el mapa, no el manual

**AGENTS.md** es el estándar abierto (60k+ repos) para instrucciones a nivel de repo: jerárquico (puede haber uno por directorio, y gana el más cercano), en Markdown, leído por casi todos los agentes. Variantes: `CLAUDE.md` (Claude Code), reglas de Cursor (`.cursor/rules`), steering de Kiro.

La regla de OpenAI es la que vale memorizar:

> **Un mapa, no un manual de 1.000 páginas.**

~100 líneas que apuntan a `docs/`: dónde está cada cosa, cómo correr el proyecto, qué convenciones no son obvias. Todo lo que el agente pueda descubrir navegando no va acá — iría a parar a cada contexto para siempre.

## El repo como sistema de registro

OpenAI llevó la idea al extremo: el repo entero es el sistema de registro del que el agente lee:

```
ARCHITECTURE.md          — el diseño en una página
docs/design-docs/        — decisiones de diseño
docs/exec-plans/
  active/                — planes en ejecución
  completed/             — planes archivados
product-specs/           — specs del producto
references/*-llms.txt    — docs de librerías en formato llms.txt
QUALITY_SCORE.md         — scorecard que el agente actualiza
```

Principio duro: **lo que el agente no ve en contexto, no existe**. Si la decisión importante vive en una conversación de Slack, para el agente nunca pasó. El repo tiene que contener su propia memoria.

## Agent Skills y progressive disclosure

Las **Agent Skills** son el formato abierto (`SKILL.md` con frontmatter `name` + `description`, más `scripts/`, `references/`, `assets/`). Su genialidad es mecánica, es progressive disclosure:

1. Metadata (nombre + descripción, ~100 tokens) — siempre visible, define si la skill aplica.
2. Instrucciones completas del SKILL.md — solo si aplica.
3. Archivos de referencia y scripts — solo cuando hacen falta.

Podés tener 50 skills instaladas y el costo fijo de contexto es solo la tabla de contenidos. Es la misma lógica del AGENTS.md-mapa, aplicada a procedimientos.

## Herramientas y MCP

El **Model Context Protocol** conecta al agente con herramientas externas (bases de datos, issue trackers, APIs). Decisiones de diseño que importan:

- Cuántas herramientas dar: cada una consume contexto con su descripción; muchas herramientas solapadas confunden más de lo que ayudan.
- Descripciones escritas para el modelo: qué hace, cuándo usarla, qué devuelve.
- Devolver solo lo relevante: una tool que devuelve 10KB de JSON cuando importan 3 campos quema contexto cada llamada.

## Hooks / middleware

Mecanismos deterministas que corren pre/post tool call:

- Lint al guardar un archivo (el agente ve el error inmediatamente).
- Bloquear comandos peligrosos antes de ejecutar.
- Forzar continuación del loop o inyectar contexto después de ciertos eventos.

Son los sensores computacionales más baratos disponibles: código normal, cero tokens.

## Subagentes y orquestación

- **Aislamiento de contexto**: la exploración vive en el subagente; al principal vuelve solo el resumen.
- **Revisores**: un agente distinto lee el diff con contexto limpio (ve lo que el implementador ya no puede ver fresco).
- **Planner/generator/evaluator**: separar decidir, producir y juzgar en contextos distintos.
- **Routing de modelos**: modelo caro para decisiones de alto riesgo, barato para el grueso.

## Sandbox y seguridad

- Permisos granulares y aprobaciones para acciones destructivas.
- Aislamiento por worktree: cada subagente trabaja en su copia, merge al final.
- Prompt injection: todo texto que entra al contexto desde fuera (web, issues, README de dependencias) es potencialmente instrucciones adversarias — el sandbox es la última línea de defensa.

## Legibilidad de la app para el agente

Si el agente va a verificar su trabajo, necesita *leer* el sistema en ejecución:

- App levantable por worktree (puerto propio, DB propia).
- Chrome DevTools Protocol para screenshots e inspección del DOM.
- Logs, métricas y trazas consultables por el agente (LogQL/PromQL).
- Todo observable vía comandos — si solo lo ve un humano con DevTools, para el agente es invisible.

## Memoria y estado entre sesiones

- **Progress files**: el agente escribe "dónde quedó" en un archivo.
- **`init.sh`**: cualquier sesión nueva arranca en el mismo estado conocido.
- **Git como log**: commits atómicos como registro de progreso recuperable.
- **Execution plans**: el plan es un artefacto versionado que sobrevive al contexto que lo creó.

## Mantenimiento del harness

El harness también se pudre: AGENTS.md desactualizado miente, skills rotas confunden, docs contradictorias dividen la atención. Prácticas: agentes de "doc-gardening" que revisan la frescura de la documentación, linters que validan que los archivos referenciados existen, retro post-sesión que detecta qué parte del entorno falló.

## Para llevar

- AGENTS.md = mapa de ~100 líneas; el repo es el sistema de registro.
- Skills + progressive disclosure: muchas capacidades, costo fijo de contexto.
- Todo lo que el agente necesita y no está en el repo/contexto, no existe.
- El harness es un codebase: también necesita mantenimiento.
