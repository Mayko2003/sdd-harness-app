## El loop agéntico mínimo

Todo harness, por sofisticado que sea, es esto:

```
prompt → modelo decide → tool call → ejecutar → resultado al contexto → repetir
```

El agente como *stateless reducer* (12-Factor Agents): recibe el estado actual del contexto, emite una acción, el sistema actualiza el estado. Construir el tuyo empieza por implementar ese loop con honestidad — todo lo demás son subsistemas alrededor.

## Los subsistemas canónicos

El paper *Harness Engineering* (arXiv 2609.00006) diseccionó 11 harnesses reales (Claude Code, Codex CLI, Gemini CLI, OpenHands, Aider, Mini-SWE-Agent, OpenCode y otros) y extrajo los subsistemas que todos comparten:

1. **Loop**: la máquina de turnos — cuándo para, cómo continúa, cómo maneja errores de tool calls.
2. **Herramientas**: el set concreto (leer, escribir, buscar, ejecutar) y sus descripciones.
3. **Gestión de contexto**: qué entra a cada turno, compaction, cómo se trunca el output.
4. **Controles de seguridad**: permisos, sandbox, aprobaciones, qué puede y qué no.
5. **Orquestación**: subagentes, handoffs, paralelismo.
6. **Superficies de extensión**: skills, MCP, ACP — cómo el usuario agrega capacidades sin tocar el núcleo.

## Hallazgos que cambian supuestos

Tres resultados del análisis que corrigen intuiciones comunes:

- **Nadie usa frameworks agénticos generales en runtime**: los harnesses de producción implementan el loop a mano. Los frameworks sirven para prototipar, no para producción.
- **Nadie recupera código con embeddings**: todo el campo corre en retrieval determinista — grep, ripgrep, tree-sitter, AST. El RAG vectorial para código que parecía inevitable simplemente no se usa en los agentes serios.
- **La política migra de prompt a configuración**: en vez de decirle al modelo "no hagas X" en el system prompt, lo determinista se vuelve config/hook/permiso. Menos tokens, más garantía.

Y un detalle de adopción: **las skills superan a MCP** como superficie de extensión — más baratas en contexto, más simples de escribir.

## Frameworks para construir

Si vas a armar tu agente/harness:

| Framework | Enfoque |
|---|---|
| **Claude Agent SDK** | El harness de Claude Code como librería: loop, tools, subagentes, hooks |
| **LangChain `create_agent` + middleware** | Loop + hooks pre/post model call y tool call; el middleware es el punto de inserción |
| **Deep Agents** | Subagentes y planificación integrados |
| **OpenAI Agents SDK** | Handoffs, guardrails, tracing |

La recomendación del análisis es construir el loop propio y usar los frameworks para las partes que sí ahorran trabajo (tracing, handoffs), no para esconder el loop.

## Evaluar tu harness

Un harness es un sistema: se mide o no mejora.

- **Evals**: conjunto de tareas con resultado conocido contra el que correr el harness. Cambió un prompt, una tool, un hook → corré las evals.
- **Medir el uso real**: dónde gasta tokens, qué tool calls repite, dónde se atasca — el ledger por corrida es diagnóstico primario.
- **Reducir al mínimo**: el harness con menos piezas que resuelve las mismas tareas es mejor — cada regla, cada tool tiene costo de contexto y de mantenimiento.
- **Reglas → scripts**: si una instrucción puede verificarse, convertirla en un check computacional (marmelab). La regla en prosa consume tokens y se puede malinterpretar; el script es gratis y cierto.

## Meta-harnesses y auto-mejora

El frente siguiente: harnesses que se mejoran a sí mismos. El paper *Agentic Harness Engineering* (arXiv 2604.25850) explora agentes que analizan sus propias fallas y modifican su harness. La skill `retro` de Pocock es la versión artesanal: post-sesión, el agente sugiere mejoras del entorno que el humano aplica.

## Para llevar

- El núcleo es el loop; todo lo demás son los ~6 subsistemas canónicos.
- Lo que los harnesses de producción NO hacen es tan informativo como lo que hacen: sin frameworks en runtime, sin embeddings para código, política en config.
- Evals + medición de tokens + poda continua = el mantenimiento del harness.
