## Separar qué/por qué, cómo y pasos

La primera habilidad de SDD es no mezclar los tres artefactos:

| Artefacto | Pregunta que responde | Ejemplo |
|---|---|---|
| **Spec** | ¿Qué tiene que hacer y por qué? | "El usuario puede filtrar pedidos por estado" |
| **Plan/diseño** | ¿Cómo lo vamos a construir? | "Filtro server-side con query param `?status=`" |
| **Tasks** | ¿En qué orden y qué unidades? | "1. Endpoint + test, 2. UI del filtro, 3. E2E" |

Mezclar el "cómo" dentro de la spec funcional envejece mal: la implementación cambia y la spec queda mentirosa. Regla práctica (Pocock): **la spec no lleva file paths ni snippets de código** — describe decisiones, no texto que expira.

## User stories + criterios de aceptación

La forma canónica sigue siendo válida:

> **Como** [rol] **quiero** [capacidad] **para** [beneficio].

Pero el user story solo no alcanza para un agente: necesita **criterios de aceptación** — condiciones verificables que convierten la intención en algo comprobable. Son el puente directo a los tests.

## EARS (Easy Approach to Requirements Syntax)

Kiro popularizó EARS en el contexto de agentes: una gramática mínima para requisitos sin ambigüedad.

```
WHEN [condición/disparador]
THE SYSTEM SHALL [comportamiento]
```

Variantes:

| Patrón | Forma | Ejemplo |
|---|---|---|
| Ubicuo | `THE SYSTEM SHALL ...` | "El sistema mostrará los totales en la moneda del usuario" |
| Por evento | `WHEN x, THE SYSTEM SHALL y` | "Cuando el usuario envía el formulario, el sistema validará el email" |
| Por estado | `WHILE estado, THE SYSTEM SHALL y` | "Mientras la sesión esté activa, el sistema refrescará el token" |
| Opcional | `WHERE condición, THE SYSTEM SHALL y` | "Donde esté habilitado 2FA, el sistema pedirá el segundo factor" |
| No deseado | `IF falla, THEN THE SYSTEM SHALL y` | "Si el pago es rechazado, el sistema mostrará el error y conservará el carrito" |

La última variante (comportamiento ante fallas) es la que más valor agrega: los requisitos de error son los que más falta hacen en specs informales.

## Escenarios Given/When/Then

Para comportamiento concreto, el formato de BDD:

```
GIVEN el usuario tiene 3 ítems en el carrito
WHEN aplica el cupón "ENVIO10"
THEN el envío queda en 0
AND el total se recalcula
```

Cada escenario es ejecutable como test de aceptación — acá SDD toca TDD: la spec escrita primero produce los tests que verifican la implementación. Un agente con escenarios Given/When/Then tiene criterio de éxito sin adivinar.

## Palabras normativas (RFC 2119)

- **MUST/SHALL**: requisito absoluto; su violación es un bug.
- **SHOULD**: recomendado; puede violarse con justificación.
- **MAY**: opcional.

Úsalas con criterio: una spec donde todo es MUST es ilegible; donde todo es SHOULD no especifica nada.

## Ambigüedad explícita

Spec Kit introdujo un marcador útil: `[NEEDS CLARIFICATION]`. En vez de que el agente adivine un requisito dudoso, la spec declara el punto abierto y hay una fase (`/speckit.clarify` o preguntas del agente) para resolverlo. La ambigüedad declarada es mejor que la ambigüedad silenciosa.

## Requisitos no funcionales, edge cases y trazabilidad

- **No funcionales**: performance, accesibilidad, seguridad, límites. Se olvidan en specs informales y el agente no los adivina.
- **Edge cases**: listas vacías, timeouts, duplicados, concurrencia. Son donde el software real vive.
- **Trazabilidad**: cada requisito → tarea(s) → test(s). Si un requisito no tiene test, o está de más o está desprotegido.

## Delta specs (OpenSpec)

La pieza clave para brownfield: en vez de reescribir la spec del sistema completo, un **cambio** describe solo el delta:

```markdown
## ADDED Requirements
### Requirement: Filtro por estado
The system SHALL allow filtering orders by status.

## MODIFIED Requirements
### Requirement: Listado de pedidos
[la versión nueva del requisito]

## REMOVED Requirements
### Requirement: Export a CSV
```

El ciclo es *propose → apply → archive*: el cambio vive en `changes/` mientras se implementa y al archivarse el delta se fusiona en la spec canónica. Así la spec queda anchored sin reescribirla cada vez.

## Antipatrones

- **Spec ilegible**: 3.000 líneas que ningún humano revisa. Si no se puede revisar, no sirve de fuente de verdad.
- **Stack en la spec funcional**: "usar Redis con TTL de 300" en un doc de comportamiento — eso va en el plan.
- **Spec drift**: la spec que nadie actualiza se convierte en ficción; peor que no tener spec.
- **Duplicar reglas globales**: convenciones del repo van en el memory bank, no repetidas en cada spec.

## Ejercicio

Tomá un requisito vago ("la app tiene que ser rápida y permitir búsqueda") y reescribilo: (a) en EARS con la variante correcta, (b) como escenario Given/When/Then concreto, (c) marcando lo que sigue ambiguo con `[NEEDS CLARIFICATION]`.
