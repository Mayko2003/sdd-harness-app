## Qué es context engineering

Definición (Anthropic): *el conjunto de estrategias para curar y mantener el conjunto óptimo de tokens durante la inferencia*. La versión operativa:

> Objetivo: el **menor conjunto de tokens de alta señal** que maximice el resultado.

No "darle todo por las dudas" sino exactamente lo necesario. Cada token irrelevante compite por la atención del modelo con los tokens que importan.

## Presupuesto de atención y context rot

Los transformers no leen gratis: a medida que la ventana se llena, el modelo empieza a mezclar instrucciones viejas con nuevas, a perder requisitos del medio del contexto y a "derivar" hacia lo más reciente. Esto es **context rot**. Consecuencias prácticas:

- Las instrucciones importantes van temprano y son pocas.
- Un contexto con un archivo de 500 líneas donde importan 20 es peor que un contexto con esas 20 líneas.
- Cuando el agente empieza a repetir errores que ya corrigió, casi siempre es context rot, no falta de inteligencia.

## Técnicas principales

**System prompt a la "altura correcta"**: ni demasiado específico (hardcodear cada caso = fragilidad) ni demasiado vago (el modelo adivina). Reglas generales + espacio para juicio.

**Herramientas bien descritas**: cada herramienta consume contexto con su descripción. Pocas herramientas con descripciones claras > muchas herramientas solapadas.

**Ejemplos canónicos**: un buen ejemplo concreto reemplaza párrafos de instrucciones abstractas.

**Just-in-time retrieval**: no cargar nada por adelantado; que el agente busque lo que necesita cuando lo necesita. El contexto se construye por demanda, no por precaución.

**Progressive disclosure**: metadata barata primero (~100 tokens por skill), instrucciones completas solo si la skill aplica, archivos de referencia solo si hacen falta. Es la misma idea: pagar contexto solo por lo que se usa.

## Tareas largas: qué hacer cuando se acaba la ventana

| Estrategia | Cómo | Cuándo |
|---|---|---|
| **Compaction** | Resumir la conversación en el lugar y seguir | Tarea continua, resumen conserva lo esencial |
| **Context reset** | Agente nuevo con un artefacto de handoff | Cambio de fase (plan → implementación), sesiones largas |
| **Notas/memoria** | El agente escribe estado estructurado a disco | Trabajo multi-sesión |
| **Subagentes** | Delegar exploración a otro contexto que devuelve solo el resumen | Búsquedas, reviews, cualquier trabajo "usa mucho, devuelve poco" |

La regla de Pocock es la versión extrema y útil: **un ticket = una ventana de contexto fresca**. Diseñá las unidades de trabajo para que quepan en un contexto nuevo.

## 12-Factor Agents

El manifiesto de Dex Horthy (HumanLayer) aplica los 12-factor apps a agentes. Los principios que más importan para entender el campo:

- **Own your prompts**: el prompt es código; versionalo, no lo delegues a un framework opaco.
- **Own your context window**: controlá exactamente qué entra a cada llamada.
- **Own your control flow**: el agente es un *stateless reducer* — recibe estado, decide una acción, el estado nuevo lo construye el sistema.
- **Agentes pequeños y enfocados** en vez de un mega-agente que hace todo.
- **Contactar al humano** con herramientas, no con instrucciones de texto.

El flujo **Research → Plan → Implement** (también de HumanLayer) — donde el agente primero produce un documento de investigación, luego un plan, y recién ahí código — es el precursor práctico directo de SDD: externalizar el pensamiento en artefactos que el humano puede revisar antes de gastar contexto en implementar.

## Para llevar

- Context engineering = curar tokens. Menor conjunto de alta señal, no máximo contexto.
- Todo el toolkit (disclosure progresivo, handoffs, subagentes, compaction) son formas de comprar contexto nuevo o conservar el que tenés.
- SDD y harness engineering son, cada uno, context engineering aplicado: la spec cura el "qué", el harness cura el "cómo trabaja".
